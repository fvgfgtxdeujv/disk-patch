# v22 报告：改派发表实现无侵入指令级追踪（附指令编码实证）

日期：2026-11-18　run 44310525456（success）　产物：`vm_trace.json` 49.7 MB / 200000 条

## 1. 为什么放弃 inline hook

| 站点 | 装 hook 后 | `jmp rsi` 之后 3 字节 | 判定 |
|---|---|---|---|
| `0x141a26451` | 存活 | `e9 7a 01`（jmp rel32 开头） | 可用但危险 |
| `0x141a353d7` | 存活 | `e9 e3 9f`（jmp rel32 开头） | 可用但危险 |
| `0x141d46a56` | **0.5 s 后 0xC0000005** | `48 89 e8` = `mov rax,rbp` | **致命** |
| `0x141e2a337` | 未测（前面已死） | — | — |

run 44307363845 的分级装 hook 日志是直接证据：装到第 3 个站点立刻 `code=0xc0000005`，
且 4 个站点的探针（进入 / 复制 / ctx 通过）全部为 0 —— 死在我们桩体执行之前。

原因：`jmp rsi` 只有 2 字节，5 字节 `call` / `jmp` 必然覆盖后面 3 字节；而 `site+2`
处是**被其它路径进入的活代码**。试过「2 字节 `eb rel8` + 邻近填充洞」方案
（run 44308138758），`find_cave` 在 ±0x70 内找不到 5 字节填充洞（4 个站点全部跳过），
该路线在这份二进制上不成立。

## 2. 新方案：只改派发表（数据），一行代码都不碰

派发器语义（已确证）：`rsi = table[op]` → `jmp rsi`。所以把 `table[op]` 换成自己的桩，
桩记录完再跳回原 handler，语义等价，且**不修改任何指令字节**。

* 每个表项一个专属桩（`STUB9_SZ=0x140`），原 handler 直接 `mov rsi, imm64` 烤进桩里
  —— 不依赖 `r15` 是 `op` 还是 `op*8`，也不需要表副本；
* 桩内 3 个探针（进入 / 复制完 / ctx 通过），用于定位崩溃点；
* 每条记录 192 字节：16 个寄存器 + `[rbp+0xBC]` + `[rbp+0xF5]` + `[IP]` + `[IP+8]` + tag。

本轮结果：**200000 条轨迹（0.5 s 就写满上限），去重 9122 种寄存器状态，进程 60 s 无异常，
结束后表已还原。**

## 3. 表结构的实测事实（修正之前的判据）

`0x1421080ab`（661 项，绝对地址风格）前 8 项：

```
141cf832a  141fc35d4  141fc35d9  141e6e631  ...
差:  +2929322     +5   -1396648      +5
```

即**成对**出现：`v[2k+1] = v[2k] + 5`。「相邻差 5」只在偶数位上成立（3/7），
所以 v22 之前按「全差 5」扫描一张表都找不到。

另外两张已知表存的是 **RVA 而不是绝对地址**：

| 表地址 | 首项 | 风格 |
|---|---|---|
| `0x1421080ab`（661 项） | `0x141cf832a` | 绝对 VA，已可打补丁 |
| `0x141da2b42`（49 项） | `0x1c9db1a` | RVA（+base 后才在 .vmp 内） |
| `0x141d8df04`（1096 项） | `0x19ddfdf` | RVA |
| `0x141c50d31` | `0` | 不是表（是 ctx 内的槽） |

RVA 风格表的派发器必然还会自己加基址，桩必须按 RVA 形式回填，本轮先跳过（不猜）。

## 4. 指令编码：实证修正

之前（v5 时期）的结论是 `op = u16@IP+7`、`rel = i32@IP+0`。**本轮实测推翻**：

在 36364 条「IP 处字节恰好仍是明文」的样本上，用「本条记录的 `[IP]` 就是下一条指令的
地址」这个关系做对齐，得

* `u16 @ IP+0 == op`：36364 条全中；
* `i32 @ IP+2 == 下一条 IP − 当前 IP`：**27273 / 27273 全中**，其余 9091 条该处已被回写密文。

指令格式：

```
+0x00  u16  op          操作码（表索引）
+0x02  i32  rel         下一条 IP = IP + rel（分支指令即跳转位移，非分支即本指令长度）
+0x06  ...  操作数
```

22 个 IP 里 4 个当下可解，其中 3 个是 `op=297` 的**分支**指令（rel 各不相同，
next 全部命中轨迹 IP）：

```
0x1422dceb3  op=297  rel=   +95  -> 0x1422dcf12
0x1422dd408  op=297  rel= -1082  -> 0x1422dcfce
0x1422dd3fe  op=297  rel=  -659  -> 0x1422dd16b
```

第 4 个（`0x1422dd056`，op=478）的 `i32@2` 不在轨迹里，该处字节应已回写密文，
属假命中，不能当编码证据。

## 5. 本轮追踪到的执行形态

* 只有 1 个 VM 实例在跑：`ctx = 0x1420c0e5f`（表 `0x1421080ab`，661 项）；
* 只涉及 **22 个 IP**，全在 `0x1422dcc57 .. 0x1422dd408` 这 ~2 KB 内；
* op 序列是 16 条一循环，例如
  `90 547 297 90 409 256 446 545 430 478 547 297 197 446 545 263` 反复，
  中间插一次 `649`；
* op 频次 top：`547 / 297 / 446 / 545`（各 ~2.7 万次）、`90 / 263`（各 ~1.8 万次）。

也就是说：这段时间 VM 在跑一个 16 条指令的死循环（消息/空闲循环），
**不是**授权校验路径。要抓授权路径，必须让 VM 在「校验上下文」里跑起来。

## 7. v23 追加实测（run 44312691938 / 44313197189）

* **表项会延迟重定位**：同一条表 `0x1421080ab`，run 44312312951 读到 `0x1cf832a`（RVA），
  run 44312691938 读到 `0x141cf832a`（绝对）。所以判据改成「等表项变成绝对地址再动手，
  最多等 20 s」，不再把 RVA 形态当「不是表」。
* 64 字节压缩记录 + 桩内 IP 去重（64K 槽）生效：4 s 内拿到 **2504 个不同 IP、66 种 op**，
  进程在 10 s 时 `0xC0000005` 退出（fakelic 开/关都崩，故与假授权无关，是本桩自身问题，
  待查——v22 的 192 字节桩可稳定跑满 60 s）。
* 去重后**明文样本率从 18% 掉到 0.2%**（2504 条里只有 2 条能解）：因为每个 IP 只采一次，
  恰好撞上「已回写密文」的概率极高。这直接引出下一步设计。
* op 频次（2504 条）：`424`(725)、`407`(685)、`547`(152)、`71`(96)、`297`(96)、`446`(77)、
  `545`(77)、`478`(64)…共 66 种；IP 覆盖 `0x142158235 .. 0x1422fb1af`（约 1.6 MB 代码）。

## 8. 下一步（下一步的实现点已明确）

**桩内做「明文自检后再落盘」**：在桩里判断 IP 处字节是否像明文
（`u16@IP < 0x800` 且 `i32@IP+2 ∈ [-0x4000, 0x4000]`），命中就把 16 字节写到
「按 IP 直接映射的槽表」里（每 IP 一条，后写覆盖）。这样跑 60 s 后，
每个执行过的 IP 都大概率留下一条**已验证的明文指令**，且不占轨迹缓冲——
得到的是完整的指令清单，而不是一堆重复样本。
