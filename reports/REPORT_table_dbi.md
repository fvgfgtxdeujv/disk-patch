# v22 报告：改派发表实现无侵入指令级追踪（附指令编码实证）

日期：2026-11-18　run 44310525456（success）　产物：`vm_trace.json` 49.7 MB / 200000 条

## 1. 为什么放弃 inline hook

| 站点 | 装 hook 后 | `jmp rsi` 之后 3 字节 | 判定 |
|---|---|---|---|
| `0x141a26451` | 存活 | `e9 7a 01`（jmp rel32 开头） | 可用但危险 |
| `0x141a353d7` | 存活 | `e9 e3 9f`（jmp rel32 开头） | 可用但危险 |
| `0x141d46a56` | **0.5 s 后 0xC0000005** | `48 89 e8` = `mov rax,rbp` | **致命** |
| `0x141e2a337` | 未测（前面已死） | — | — |

run 44307363845 的分级装 hook 日志是直接证据：装到第 3 个站点立刻 `code=0xc0000005`，
且 4 个站点的探针（进入 / 复制 / ctx 通过）全部为 0 —— 死在我们桩体执行之前。

原因：`jmp rsi` 只有 2 字节，5 字节 `call` / `jmp` 必然覆盖后面 3 字节；而 `site+2`
处是**被其它路径进入的活代码**。试过「2 字节 `eb rel8` + 邻近填充洞」方案
（run 44308138758），`find_cave` 在 ±0x70 内找不到 5 字节填充洞（4 个站点全部跳过），
该路线在这份二进制上不成立。

## 2. 新方案：只改派发表（数据），一行代码都不碰

派发器语义（已确证）：`rsi = table[op]` → `jmp rsi`。所以把 `table[op]` 换成自己的桩，
桩记录完再跳回原 handler，语义等价，且**不修改任何指令字节**。

* 每个表项一个专属桩（`STUB9_SZ=0x140`），原 handler 直接 `mov rsi, imm64` 烤进桩里
  —— 不依赖 `r15` 是 `op` 还是 `op*8`，也不需要表副本；
* 桩内 3 个探针（进入 / 复制完 / ctx 通过），用于定位崩溃点；
* 每条记录 192 字节：16 个寄存器 + `[rbp+0xBC]` + `[rbp+0xF5]` + `[IP]` + `[IP+8]` + tag。

本轮结果：**200000 条轨迹（0.5 s 就写满上限），去重 9122 种寄存器状态，进程 60 s 无异常，
结束后表已还原。**

## 3. 表结构的实测事实（修正之前的判据）

`0x1421080ab`（661 项，绝对地址风格）前 8 项：

```
141cf832a  141fc35d4  141fc35d9  141e6e631  ...
差:  +2929322     +5   -1396648      +5
```

即**成对**出现：`v[2k+1] = v[2k] + 5`。「相邻差 5」只在偶数位上成立（3/7），
所以 v22 之前按「全差 5」扫描一张表都找不到。

另外两张已知表存的是 **RVA 而不是绝对地址**：

| 表地址 | 首项 | 风格 |
|---|---|---|
| `0x1421080ab`（661 项） | `0x141cf832a` | 绝对 VA，已可打补丁 |
| `0x141da2b42`（49 项） | `0x1c9db1a` | RVA（+base 后才在 .vmp 内） |
| `0x141d8df04`（1096 项） | `0x19ddfdf` | RVA |
| `0x141c50d31` | `0` | 不是表（是 ctx 内的槽） |

RVA 风格表的派发器必然还会自己加基址，桩必须按 RVA 形式回填，本轮先跳过（不猜）。

## 4. 指令编码：实证修正

之前（v5 时期）的结论是 `op = u16@IP+7`、`rel = i32@IP+0`。**本轮实测推翻**：

在 36364 条「IP 处字节恰好仍是明文」的样本上，用「本条记录的 `[IP]` 就是下一条指令的
地址」这个关系做对齐，得

* `u16 @ IP+0 == op`：36364 条全中；
* `i32 @ IP+2 == 下一条 IP − 当前 IP`：**27273 / 27273 全中**，其余 9091 条该处已被回写密文。

指令格式：

```
+0x00  u16  op          操作码（表索引）
+0x02  i32  rel         下一条 IP = IP + rel（分支指令即跳转位移，非分支即本指令长度）
+0x06  ...  操作数
```

22 个 IP 里 4 个当下可解，其中 3 个是 `op=297` 的**分支**指令（rel 各不相同，
next 全部命中轨迹 IP）：

```
0x1422dceb3  op=297  rel=   +95  -> 0x1422dcf12
0x1422dd408  op=297  rel= -1082  -> 0x1422dcfce
0x1422dd3fe  op=297  rel=  -659  -> 0x1422dd16b
```

第 4 个（`0x1422dd056`，op=478）的 `i32@2` 不在轨迹里，该处字节应已回写密文，
属假命中，不能当编码证据。

## §12 真实状态重放解码（v26→v34，重放 ok 98.1%）

### 12.1 方法：真实状态重放（不破密码，用真密钥）
每条派发记录附带 ① 32B 包密文快照（[IP..IP+32)）② ctx 页 4KB 快照（stub12 的 rep movsq 从非页对齐 rbp 复制）。
用 unicorn 重建运行时环境（dump 静态映射 + 表=桩指针 + 桩区可执行 + bc_window 字节码快照 + 低区零页），
从记录 i 的 handler body 开始执行，截断于下一记录的桩入口 → 解码正确性自证（next_op == 下一记录 tag）。

## §13 定位授权算法（marker 差分 + 双 run 序列对齐）

### 13.2 双 run tag 序列对齐（决定性）
art23c（无授权）vs art33（fakelic）difflib 对齐：

### 13.3 授权门（9-op 输入相关块）
tags: 547,297,406,446,545,263,446,545,430 —— 完整条件判断结构。
写值序列（低区栈 0x13fff28）：0x13ffef8(指针) → **0xc0000004** → 0x1d0000 → 0x1d0045 → 0x1d7000 → 0x1d7d2d
- 0xc0000004 = STATUS_INFO_LENGTH_MISMATCH（异常状态值入栈——VM 内部异常处理/探测）
- 0x1d0000/0x1d7000 = **运行时堆区指针**（VM 启动时该区尚不存在，运行中分配）
- 0x1d0045/0x1d7d2d = 区内偏移指针 → VM 在 0x1d0000 堆上遍历结构
两路径在 op 906（478,305,407...）汇合。

### 13.4 结论：授权校验 = 主 2504-op VM 程序
门只判"有无授权数据"；主程序对堆中的授权结构做完整计算（结构相同、数据不同 →
op 序列一致）。**授权算法的数据在 0x1d0000 堆区**（marker 扫描无明文 → 已被原生侧加密/变换）。
计算产物（低区栈单次写入值）：0x50fa8461、0x9aa3a68d、0x80739dfb、0x6e6a072、0x1ea9d、0x9dfb、0x5fb0c

## §14 资源容器再解析：§13.6 修正（TEMP/PRVAH/OPCO/LEVL ≠ Themida 密钥材料）

### 14.1 容器提取
art41/heap_snap_5.4s.bin（20MB，VA 0x100000..0x1400000）内偏移 0xd0000（=VA 0x1d0000）
发现 MZ/PE：12KB PE32+，ImageBase 0x180000000，无入口点，两节
.rdata（vsz 0x100）+ .rsrc（vsz 0xd78）。已存
`/workspace/dgwork/res_parse/themida_container_0x1d0000.bin`（名沿用，见 14.4 修正）。

### 14.2 .rsrc 标准目录树解析（决定性）
遍历资源目录得到 **MUI(1/1033, 240B)、WEVT_TEMPLATE(1/1033, 1986B)、16(1/1033, 944B)**
三个标准资源类型——不是 TEMP/PRVAH/OPCO/LEVL 四个"Themida 资源"。

### 14.3 TEMP/PRVAH/OPCO/LEVL 的真实身份
四个标记位于 .rsrc 原始数据内（0x224c/0x2650/0x2698/0x2710），是
**WEVT_TEMPLATE 二进制格式的标准 chunk 标签**（TTBL/TEMP/PRVAH/OPCO/LEVL，
Windows 事件模板格式：PRVAH=provider 头、TTBL=模板表、TEMP=模板、
OPCO=opcode 表、LEVL=level 表）。邻近 UTF-16 明文
`Microsoft-Windows-OLEACC/Debug` 证实该 12KB PE 是 **oleacc.dll 的
ETW 事件提供程序模板资源**在堆里的拷贝（运行期 ETW 注册的正常产物），
与 Themida/WinLicense 授权机制无关。

### 14.4 交叉验证
art42/heap_snap_5.1s.bin（0x1b0000 窗口 256KB）同一内容出现在 VA 0x1b0000，
ImageBase 0x100000000000（≠0x180000000）——两次运行同款 PE、不同 ImageBase、
不同堆地址：是系统侧复制的资源对象，不是固定授权容器。
TEMP 内 32B blob（001a3313 23a87a5b 8a02e77d 8cbccea7…）实为 ETW 模板元数据，
**§13.7"密钥材料在 TEMP/PRVAH/OPCO/LEVL 中"作废**。

### 14.5 授权结构位置修正
5.4s 快照中 0x1d0000..0x1d3000 之后全部为零，0x1e0000 处是 "Actx " 头的
SxS Activation Context 结构（含 shell32/Common-Controls manifest 路径）——
5.4s 时低区堆只剩 Windows 运行时对象，**VM 运行期（0.5-4s）的授权结构已被释放**。
门写入指针 0x1d0000/0x1d7000 指向的堆块在快照时刻不存在 →
