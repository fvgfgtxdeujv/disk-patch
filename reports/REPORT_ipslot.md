# IP 槽恢复 —— DiskGenius VM 真实派发结构

日期：本轮（承接 `REPORT_dispatch_v2.md` 第九节第 1 条）
状态：**真实派发结构已还原，cmp 链方案在这份载荷上被判死**

---

## 一、结论

这份载荷的 VM **不存在 cmp 链派发**。它的每一步是：

```
and  r12, 0xffff              ; 取 16 位 opcode
shl  r12, 3                   ; opcode * 8
add  r10, r12                 ; table + opcode*8
mov  r11, qword ptr [r10]     ; handler = table[opcode]   ← 跳表
...
mov  rsi, rbp
add  rsi, 0x92                ; ctx + IP 槽
mov  rsi, qword ptr [rsi]     ; IP = ctx[0x92]（二级间接）
add  rsi, 5                   ; 定位本步长度字段
movsxd r10, dword ptr [rsi]   ; 本步长度（流内 dword）
...
mov  rbx, rbp
add  rbx, 0x92
add  qword ptr [rbx], r10     ; ctx[0x92] += 长度
jmp  r11                      ; 跳到该 opcode 的 handler
```

也就是「**跳表 + IP 自增 + 寄存器间接跳**」，跳表用 `mov reg,[mem]` + `jmp reg` 拆成两条，
而不是 `jmp [mem]`。现有 `x86il_dispatch.handle_jumptable()` 只认后者，所以整类形态都没覆盖。

---

## 二、硬证据：两套候选完全不相交

| 量 | 值 |
|---|---|
| IP 槽站点（`add [ctx+slot],len; jmp reg`） | **3314** |
| cmp 链候选 handler 目标（去重） | **3326** |
| **两者交集** | **0** |
| 候选里「块尾落在 IP 站点」的数量 | **0** |

3314 个真实派发点与 3326 个 cmp 链候选，一个都不重合。这不是「召回率不够」，
是**两套东西根本不是同一个机制**——`discover_handlers` 找到的全是 junk 代码里的伪候选。

## 三、量化结果

### 3.1 IP 槽不止一个

| 槽偏移 | 站点数 | 占比 |
|---|---|---|
| 0x18 | 1454 | 43.9% |
| 0x92 | 1017 | 30.7% |
| 0x120 | 630 | 19.0% |
| 0x55 | 127 | 3.8% |
| 0x17A | 86 | 2.6% |

而且是**按地址段分化**的：

| 槽 | 0x0 段 | 0x200000 段 | 0x400000 段 | 0x600000 段 |
|---|---|---|---|---|
| 0x18 | 2 | 15 | **993** | 444 |
| 0x92 | 69 | **948** | 0 | 0 |
| 0x120 | 47 | 101 | 183 | 299 |
| 0x55 | **127** | 0 | 0 | 0 |

说明：这不是「一个 VM 一个上下文」，而是**多个上下文实例/多份翻译结果**，
各自把 IP 放在不同的槽里。单一 `--ip-offset` 参数在这份载荷上是不够的。

### 3.2 派发确实走跳表

| 形态 | 站点数 | 占比 |
|---|---|---|
| 表项 = base + idx*8（`shl rI,3` + `add rBase,rI` + `mov rD,[rBase]`） | 1573 | 47.5% |
| 表项读取但索引不是 *8 | 935 | 28.2% |
| 回看窗口内没找到表项读取（junk 插队，回溯失败） | 806 | 24.3% |

在 1573 个确认走表查询的站点里，**1086 个（69%）带 `and rX, 0xffff`** ——
这是 16 位 opcode 的第三次独立印证（前两次：`0f b7` 有 19636 处、`0f b6` 只有 1147 处；
`cmp r13w, imm` 形态大量出现）。

### 3.3 步长是流内 dword

每个站点前面必然有一个 `movsxd rY, dword ptr [rZ]`，`rZ` 由 IP 加一个小偏移得到。
偏移分布很散（0x0 / 0x2 / 0x4 / 0x6 / 0x8 / 0x7 / 0x9 / 0xa / 0x5 各占 3%~17%），
说明长度字段在 VM 字节流里的位置是逐条变化的——字节流是**自描述**的：
每条 VM 指令自带 4 字节长度。

对做 devirtualization 来说这是好消息：只要拿到 IP 初值和上下文，就能按长度字段线性走完字节流，
不需要先恢复 opcode 表。

### 3.4 块不是线性相邻

相邻站点（间距 <0x400）之间，从上一站点往下顺序解码能精确落到下一站点的只有 **2.8%**（27/960）。
所以不能靠「顺序扫描切块」恢复基本块——这也是为什么整段代码里塞满了 junk 岛。
块与块之间靠 `jmp r11` 动态连接。

## 五、下一步（按性价比排）

1. **把 `mov rD,[tbl+idx*8]; jmp rD` 做成第六种派发形态**，接进 `x86il_dispatch`。
   现有 `handle_jumptable` 只需要多一种前置模式：先识别 `shl rI,3 / add rBase,rI`，
   再把 `mov rD,[rBase]` 当作表项读取，`jmp rD` 当作派发终止。表项值就是 handler 地址，
   可以像现有 `jmp [mem]` 分支一样直接读出来。**这是最短路径，预计能直接拿到 1573 个真实派发点。**
2. **多上下文支持**。槽 0x18/0x92/0x120/0x55 要分开跟踪，`--ip-offset` 改成可给多个，
   或者按地址段自动分段。
3. **沿字节流走**。有了「每条指令自带 dword 长度」这个性质，可以先不碰 handler、
   直接把 VM 字节流切成指令序列，再逐条对照 handler。
4. **块起始恢复**。站点是块尾，块首还得靠 `jmp r11` 的目标集合来定；
   目标来自 `table[opcode]`，所以第 1 条做完之后块首集合就自然有了。

## 六、诚实的限制

- **回溯解码不是完备的**：`back_context` 靠「从多个起点试解码、取能精确落在站点上的最长序列」，
  24.3% 的站点因此找不到表项读取。真实覆盖率只会更高，不会更低，但具体数字还不确定。
- **槽偏移的含义未证实**：0x18/0x92/0x120 只是「IP 在这个偏移」，为什么是这三个值、
  是否对应三个独立执行上下文，没有验证。
- **`0x55` 那 127 个站点集中在 0x0 段**，形态上也像 IP 自增，但可能是别的用途
  （例如 VM 入口/退出的状态保存），没有单独确认。
- 所有数字来自这一份 13.9MB 载荷；换保护版本后槽偏移、opcode 宽度都要重新标定。

## 七、第六种形态已落地（本轮新增）

上一节第 1 条「把 `mov rD,[tbl+idx*8]; jmp rD` 做成第六种派发形态」已经做完了。

### 7.1 实现要点

1. **形态识别**：在 `scan_block` 里维护三个小状态
   - `scaled`：被 `shl rX, 3` 乘过 8 的寄存器
   - `tbase`：表基址寄存器 → 索引寄存器（来自 `add rA, rI` 或 `lea rA,[rB+rI*8]`）
   - `baseva`：寄存器 → 静态已知地址（`movabs` / `lea rip`）
   遇到 `mov rD, [rA]` 且 `rA` 在 `tbase` 里 → 记下 `tbl = (rD, 索引寄存器, 表地址, 读表时的选择子)`；
   之后遇到 `jmp rD` 就兑现成派发点。

2. **种子不能靠紧邻**。真实代码里 `mov r11,[r10]` 在 0x141D34F0D、`jmp r11` 在 0x141D34F54，
   中间隔了二十多条 junk。所以种子锚点换成 **`shl rX, 3`**（14MB 里 4292 处），
   从索引左移处起扫，junk 会被顺序跳过，最后照样走到 `jmp`。

3. **选择子要在读表那一刻快照**。`mov` 和 `jmp` 之间的 junk 里全是 `mov reg,[mem]`，
   会把当前选择子改掉；比对必须用读表时的那个（`sel_at_read`），否则一个都匹配不上
   ——这个 bug 让结果一度从 7473 掉到 2。

4. **早退要让路**。原来的「24 条没比较过选择子就放弃」会误杀跳表块（它压根没有 cmp），
   改成「且 `tbl/tbase/scaled` 都为空」才放弃。

5. **表基址可解析时直接读表**：`read_table()` 按 8 字节表项逐项读，值落在载荷内才算 handler。
   这条路径在合成载荷上验证通过（自检第 12 项），真实载荷上因为基址是运行期二级间接，命中 0。

### 7.2 实测

| 指标 | 值 |
|---|---|
| 第六形态派发点（去重） | **3244** |
| 与 IP 槽站点（3314）交集 | **3225** |
| **覆盖率** | **97.3%** |
| 表基址可静态解析 | 0（全是运行期 `mov rB,[rX]`） |
| 真实载荷总耗时 | 17.8s（原 11.2s，多了 4292 个锚点的块扫描） |

改动前后对比：第六形态识别前，cmp 链候选与 IP 站点**交集 0**；识别后，派发面覆盖 **97.3%**。

### 7.3 仍然拿不到 handler 地址

`table[opcode]` 的表基址是运行期从内存二级间接读出来的（`mov r10,[r13]` 之类），
静态推不出来，所以 **opcode → handler 的映射在这份载荷上依然不可得**。
能拿到的是「派发点在哪儿」和「索引寄存器是谁」，这已经足以支撑下一步：

- 在运行期把 `table` 指针 dump 出来（一次内存断点即可），套上这 3244 个派发点就能出完整映射；
- 或者按第五节第 3 条，沿字节流的 dword 长度字段先切出 VM 指令序列。
